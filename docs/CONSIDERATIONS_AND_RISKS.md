# atsumate 開発・運用における懸念事項・リスク分析および対策集
(Considerations, Risks & Mitigation Strategies)

本ドキュメントは、「atsumate」の企画・設計から実装・本番運用へ進むにあたり、想定される技術的・運用的な懸念事項（リスク）と、それを解決するための具体的な対策・設計方針をまとめたものです。

---

## 1. インフラ・ネットワーク・デプロイ面のリスク ⚠️

### 1.1 Vercel（クラウド）からローカルの `langgraph_sample` に繋がらない問題
- **リスク内容**:
  Next.js Webフロントエンドを Vercel にデプロイした場合、Vercel のサーバーレス関数（クラウド環境）から、ローカルマシン（Mac）で起動している `langgraph_sample`（`http://127.0.0.1:8000`）へは直接通信できません。
- **具体的な対策方針**:
  1. **開発・検証フェーズ**:
     - `Cloudflare Tunnel`（無料）または `ngrok` を利用し、ローカルの FastAPI に一時的なパブリックURL（例: `https://xxxx.trycloudflare.com`）を付与して Vercel の環境変数 `LANGGRAPH_API_URL` に設定する。
     - あるいは、Web 側もローカル環境（`http://localhost:3000`）で起動して開発・テストを行う。
  2. **本番運用フェーズ**:
     - `langgraph_sample` をコンテナ化（Docker）し、Cloud Run、Railway、Render、または VPS などのクラウド環境にデプロイする。
     - または、`langgraph_sample` の内部設定で、Ollama（ローカルLLM）だけでなくクラウドLLM（Google Gemini API / OpenAI API）へ容易に切り替えられるように設計しておく（環境変数 `LLM_PROVIDER=ollama|gemini|openai`）。

### 1.2 Vercel サーバーレス関数の実行タイムアウト
- **リスク内容**:
  Ollama のローカルモデルによる Vision 画像解析や、複数ステップの ReAct ツール実行は、ハードウェア性能によって 15秒〜30秒以上かかる場合があります。Vercel の標準 API（Hobbyプラン）は 10秒〜15秒でタイムアウトしてしまいます。
- **具体的な対策方針**:
  1. **SSE（Server-Sent Events）ストリーミングの徹底**:
     - `langgraph_sample` に実装済みの `POST /v1/conversations/{id}/messages/stream` をそのまま透過し、Next.js 側でも SSE でクライアントへチャンクを即座に返し続けることで、コネクション切断（タイムアウト）を防ぐ。
  2. **非同期ジョブ化（レシート解析時）**:
     - レシート解析に時間がかかる場合、アップロード直後に「解析中」ステータスを返し、完了時にポーリングまたは SSE で通知する非同期設計を導入する。

## 2. AI・Vision（レシートOCR）の精度・エッジケース面のリスク 🧾

### 2.1 数字の読み間違い・税抜税込の混同による金銭トラブル
- **リスク内容**:
  居酒屋の長いレシート、シワの寄ったレシート、薄暗い席での撮影、手書き領収書の場合、ローカルの小型Visionモデル（7B〜9Bクラス）では「3と8」「0と6」の誤認識や、税抜小計を合計と誤認するリスクがあります。会計アプリにおいて金額ミスは利用者の信頼失墜に直結します。
- **具体的な対策方針**:
  1. **Human-in-the-Loop（人間の確認・修正UX）の徹底**:
     - AIの解析結果は「確定」ではなく、必ず「ドラフト（下書きプレビュー）」として表示する。
     - 幹事がスマホ画面上で「店名」「合計」「お酒/食事の品目」をワンタップで修正・確認できる UI/UX を必須設計とする。
  2. **システム側での合計検算バリデーション**:
     - 「各品目の合計金額」と「レシート全体の支払総額」が一致しているかを自動計算。
     - 差額がある場合は「⚠️ 明細合計（¥12,400）と記載総額（¥13,200）に差額があります。サービス料または読み取りミスがないかご確認ください」と警告トーストを表示する。

## 3. アカウント不要（ゲスト参加型）のセキュリティリスク 🔒

### 3.1 他人の回答の不正書き換え・なりすまし
- **リスク内容**:
  「招待URLを開いて名前を選ぶだけで回答できる」手軽さの裏返しとして、URLを知っている悪意ある第三者や参加者が、他の人（例: 田中さん）の出欠を勝手に「不参加」に変更したり、架空の立替経費を登録できてしまうリスクがあります。
- **具体的な対策方針**:
  1. **ゲストセッショントークン (`guestToken`) の発行**:
     - 参加者が初回出欠登録した際、ブラウザの `LocalStorage` または Cookie に一意の UUID (`guestToken`) を保存。
     - 以降の回答変更は、このトークンを保持している端末からのみ許可する。
     - 別の端末から修正したい場合は、初回登録時に送信された「自分専用の回答変更URL」からアクセスさせる。
  2. **厳格な権限分離（Role-Based Access Control: RBAC）**:
     - **幹事（ログイン済みオーナー）のみ可能**: イベント情報の変更・中止、立替経費の承認・確定、精算ステータスの強制変更。
     - **ゲスト参加者**: 自身の出欠回答、自身の立替経費の申請、自身の送金完了報告のみ可能。

## 4. 会計・割り勘計算における人間関係トラブル防止設計 💰

### 4.1 端数処理（10円・100円単位の丸め）の不信感
- **リスク内容**:
  「1人あたり ¥4,333」のように割り切れない場合、端数を誰が負担するか、あるいは切り上げて幹事が浮いたお金を懐に入れているのではないかという不信感が生じるリスクがあります。
- **具体的な対策方針**:
  1. **端数処理ポリシーの事前選択と可視化**:
     - 幹事がイベント作成時または精算時に以下から選択可能にする：
       - **100円単位切り上げ**: 1人 +67円（端数の余剰金は「幹事へのお礼・会場予約手数料」として明記）
       - **100円単位切り捨て**: 1人 -33円（差額は「幹事が自己負担」として明記）
       - **1円単位の完全均等**: PayPay送金等で1円単位で正確に割り切る
  2. **透明性の確保**:
     - 精算画面に「総支払額」「各人の計算根拠」「端数の行き先」を明瞭に表示する。

### 4.2 ドタキャン・当日遅刻発生時のキャンセル料トラブル
- **リスク内容**:
  「当日に2名が体調不良でドタキャンしたが、お店はコース代金の100%を請求してきた」場合、そのキャンセル料をドタキャンした本人が全額払うのか、参加者全員で被るのかで揉めるケースが多発します。
- **具体的な対策方針**:
  1. **キャンセル料按分シミュレーション機能**:
     - AIエージェントに「キャンセル料の扱い」を相談可能にする（例:「ドタキャン者2名にコース代（食事のみ）を請求し、席料・ドリンク飲み放題分は参加者で按分する」などの折衷案を提示）。

## 5. メール送信・通知の到達率リスク ✉️

### 5.1 迷惑メール判定（スパムフォルダ行き）
- **リスク内容**:
  新規取得ドメインから参加者宛に一斉にリマインドメールを送った場合、Gmail や日本の携帯キャリアメール（docomo, au, SoftBank）のスパムフィルターに弾かれるリスクがあります。
- **具体的な対策方針**:
  1. **独自ドメインの DNS 認証（SPF / DKIM / DMARC）**:
     - Resend のドメイン登録時に、DNS レコードを正しく設定し、DMARC ポリシー（`v=DMARC1; p=none; ...`）を整備して送信ドメインの信頼性を確立する。
  2. **「メールだけに頼らない」マルチチャネル設計**:
     - 日本のイベント文化においては、**「LINEグループへの一括コピペ」** および **「スマホカレンダー登録（Google/iPhone）」** が最も確実でユーザーに喜ばれます。
     - UI上でも「メール送信」だけでなく「LINE共有テキストをコピー」を優先配置する。

## 6. Flutter（モバイルアプリ）開発時の注意点 📱

### 6.1 API のバージョニングと互換性維持
- **リスク内容**:
  Web はデプロイすれば全員が即座に最新版を使いますが、Flutter モバイルアプリはユーザーがアプリをアップデートするまで古いバージョンのまま残り続けます。Next.js 側の API を後から変更した際に、古いモバイルアプリがクラッシュするリスクがあります。
- **具体的な対策方針**:
  1. **API パスのバージョニング**:
     - 必ず `/api/v1/...` のようにバージョンを明記したエンドポイント設計を徹底する。
  2. **レスポンスの非破壊的変更**:
     - フィールドを削除・リネームせず、新しいフィールドを追加する形で拡張する。

## 7. リスク対策まとめチェックリスト

| 分類 | リスク項目 | 対策ステータス |
|:---|:---|:---:|
| **インフラ** | Vercel とローカル `langgraph_sample` の通信 | Cloudflare Tunnel / クラウドコンテナ化で解決可能 |
| **インフラ** | Vercel タイムアウト (10秒制限) | SSEストリーミング / 非同期ジョブで解決可能 |
| **AI/Vision** | レシートの誤認識・数字間違い | Human-in-the-Loop確認画面 & 合計自動検算で防止 |
| **セキュリティ**| ゲスト参加時のなりすまし・改ざん | guestToken セッション & 幹事RBAC分離で防止 |
| **会計** | 端数処理・ドタキャンの人間関係トラブル | 透明な端数ポリシー明示 & 按分シミュレータで防止 |
| **通知** | メールの迷惑メール判定 | SPF/DKIM設定 & LINE/カレンダー併用で防止 |
| **モバイル** | FlutterアプリのAPI後方互換性 | `/api/v1` バージョニング徹底で防止 |
