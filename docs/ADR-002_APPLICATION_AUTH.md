# ADR-002: Web・モバイル共通のアプリケーション認証基盤

- 状態: 採用
- 決定日: 2026-09-10

## 背景

ADR-001で導入したSupabase Authは廃止し、Keycloakにも戻さない。Webと将来のFlutterアプリから同じアカウントを利用しつつ、認証サービス固有のユーザーIDやセッションへ業務データを依存させない構成が必要である。

## 決定

- ユーザーの主体IDはatsumate専用PostgreSQLの`User.id`とする。
- WebはAuth.js v5のJWT Cookieセッションを使用する。
- モバイルはNext.js APIが発行する15分有効のアクセストークンと、30日有効の更新トークンを使用する。
- 更新トークンはハッシュ保存し、使用時にローテーションする。再利用を検知した系列は失効させる。
- Googleとメール＋パスワードを認証方法とする。Googleアカウントはprovider ID、メールアカウントは確認済みメールアドレスで`User`へ紐付ける。
- パスワードはscryptでハッシュ化し、平文では保存しない。
- Web CookieとモバイルBearerの検証結果を共通の認証処理で`User.id`へ変換し、Route HandlerはそのIDで認可する。
- SupabaseとKeycloakのSDK、設定、実行時依存を撤去する。ファイル保存とリアルタイム更新の基盤は、対象機能の着手時に別途決定する。

## セキュリティ境界

- `AUTH_SECRET`、`MOBILE_TOKEN_SECRET`、`GUEST_TOKEN_PEPPER`は別々の値を使用する。
- メール確認とパスワード再設定には、期限付き・一回限りの不透明トークンを使用し、DBにはハッシュだけを保存する。
- ログイン、登録、パスワード再設定は送信元とメールアドレス単位で試行回数を制限する。
- Google IDトークンは署名、issuer、audience、メール確認状態を検証する。
- 認証失敗時は、メールアドレスの登録有無を応答から判別できないようにする。
- パスワード変更時は認証バージョンを更新し、既存のWebセッションとモバイルトークンを失効させる。

## モバイル連携

Flutterは`/api/v1/auth`で登録・ログイン・更新・ログアウトを行い、`/api/v1`へBearerアクセストークンを送信する。WebのCookie、Google IDトークン、パスワードそのものをアプリ用アクセストークンとして使い回さない。

iOS版でGoogleログインを公開する前に、App Storeのログインサービス要件を確認し、必要な同等ログイン方式を追加する。

## 影響

- Webとモバイルでユーザーと業務データを共有できる。
- 認証データの保存、メール確認、トークン失効、レート制限をatsumate側で運用する責任が生じる。
- Supabase Auth利用者の移行は行わない。既存の業務データと`User.id`による関連は維持する。
